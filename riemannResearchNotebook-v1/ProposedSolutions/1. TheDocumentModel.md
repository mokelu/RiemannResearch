## 1. The problem, explained like you're five

Imagine you ask a friend to tell you a story.

Your friend is a great storyteller. When they talk, they make their voice go
loud for the exciting parts, quiet for the secrets, and they point at the
picture book: "this part is the title," "this part is a list," "this part
someone actually said."

Now imagine your notebook made your friend sign a rule first: *"You may only
answer by putting each sentence into a little box, and every box must have a
label on it. No titles. No voice changes. Nothing extra."*

Your friend obeys. You get a pile of little labeled boxes. Every sentence is
there. But the **storytelling is gone** — the title, the chunks, the
excitement. All that's left is a flat row of boxes, and it reads like a
robot's shopping list.

And here's the part that matters: the page that shows you the boxes
(the renderer) cannot bring the storytelling back. It never received it.
You threw the writing away **before** the answer even arrived. Nothing
downstream can recover a thing that was never sent.

That rule we signed is our current prompt and schema: the AI may return only
`{ id, text, tag }` sentences plus relations, "plain text, no prose." So the
moment the AI stops replying in fancy formatted text and starts replying in
our JSON, we lose every part of its writing that made it feel like a real
answer.

## 2. The problem, stated precisely

The current contract destroys the presentation layer at the source:

- `contract/prompt.js` says: `"text" is the sentence itself, plain text` and
  `You do not write prose.`
- `schema.js` allows exactly `{ nodes: [{id, text, tag}], relations: [...] }`
  — flat, unordered-in-meaning, styleless.
- `projections/document.js` can only do
  `nodes.map((node) => node.text).join("")` — it invents nothing, because
  inventing in the renderer is banned (rightly).

The root cause is one conflation: **the reasoning graph is also serving as
the document model.** A graph knows *what is claimed and what supports what*.
It does not know — and should not be asked to know — *what the reader sees
first, where a new paragraph starts, or which line is a title*. Those are two
different facts about the same answer, stored as one.

Any fix that bolts style onto the node list (`{ tag: "CLAIM", style:
"paragraph" }`) makes the same mistake smaller. The fix is to stop
conflating the two dimensions.

## 3. What is NOT the answer

1. **Two-pass generation** (AI writes Markdown, a second turn converts it to
   JSON). Two representations of one answer: they drift, the second pass can
   rewrite the first, and cost and latency double. Rejected.
2. **Storing raw Markdown as the content** (a `text` field full of
   `#`, `**`, `-`). The style becomes an unparseable string hiding inside
   data; every projection would have to re-parse text syntax, and the
   reasoning graph still wouldn't exist. Markdown is a *serialization*, not
   a *model*. Rejected.
3. **Renderer-invented layout** (Document view heuristically guesses titles
   and paragraphs from tags). The renderer must never invent what the AI
   never said. Rejected — it violates the projection rule we just fought for.

## 4. The solution: one JSON, two dimensions

The AI still produces **one thing, in one pass**. It is simply richer JSON:

```text
AI
 ↓
one JSON document
 ├── blocks   ← how the answer READS     (document structure)
 ├── nodes    ← what the system KNOWS    (reasoning structure)
 └── relations ← how the knowledge CONNECTS
 ↓
validate at the boundary (one check, both dimensions)
 ↓
the Space stores it
 ↓
each projection reads the slice it needs
```

The mental model changes from `Node = sentence = document` to:

```text
Document = ordered blocks       (presentation dimension)
Node     = semantic unit        (reasoning dimension)
A block may contain several nodes; a node appears in exactly one place.
The two dimensions reference each other but are not the same thing.
```

### 4.1 The canonical shape

```json
{
  "blocks": [
    { "type": "heading", "level": 1,
      "runs": [ { "kind": "text", "text": "Why GTA 6 Could Be a Beautiful Game" } ] },
    { "type": "paragraph",
      "runs": [
        { "kind": "node", "ref": "n1" },
        { "kind": "text", "text": " In other words, the spectacle is structural, not cosmetic." }
      ] },
    { "type": "list", "ordered": false,
      "items": [ { "runs": [ { "kind": "node", "ref": "n2" } ] } ] },
    { "type": "quote",
      "runs": [ { "kind": "node", "ref": "n3" } ] }
  ],
  "nodes": [
    { "id": "n1", "text": "The lighting engine makes every street a different mood.", "tag": "CLAIM" },
    { "id": "n2", "text": "Trailer shots show unprecedented NPC density.", "tag": "EVIDENCE" },
    { "id": "n3", "text": "A living world is what makes the experience memorable.", "tag": "HYPOTHESIS" }
  ],
  "relations": [
    { "from": "n2", "relation": "supports", "to": "n1" }
  ]
}
```

### 4.2 The one design decision that decides everything: content lives ONCE

If a block held its own copy of a sentence's text *and* the node held it too,
we would be back to two parallel things — drift inside a single document, the
exact sin the two-pass approach was rejected for. So:

- **`nodes` own all reasoning-sentence content.** Text is written once.
- **`blocks` are pure structure.** A block is an ordered list of *runs*; a run
  is either a **reference** to a node (`{ "kind": "node", "ref": "n1" }`) or a
  small amount of **connective prose that carries no reasoning**
  (`{ "kind": "text", "text": "In other words, …" }`).
- **Every node must be referenced by at least one block** (or the boundary
  rejects it: known but invisible is not allowed), and every `ref` must
  resolve to an existing node.

The boundary can enforce all of this — it already does the same style of
cross-check for relations pointing at missing nodes.

### 4.3 Block and run grammar (v1)

Block types — deliberately small:

| type      | payload                | renders as |
|-----------|------------------------|------------|
| `heading` | `level: 1–6`, `runs`   | `<h1>`–`<h6>` |
| `paragraph` | `runs`               | `<p>` |
| `list`    | `ordered: bool`, `items: [{ runs }]` | `<ul>`/`<ol>` |
| `quote`   | `runs`                 | `<blockquote>` |
| `code`    | `language?`, `text`    | `<pre><code>` |

Run types:

| kind    | payload      | rule |
|---------|--------------|------|
| `node`  | `ref`        | must resolve to a node id |
| `text`  | `text`       | plain; may carry inline marks (4.4) |

**Not in v1:** tables, images, footnotes, nesting blocks inside blocks. The
grammar is closed by `additionalProperties: false`, same as today's schema —
anything unknown fails visibly at the boundary.

### 4.4 Inline styling is data, not syntax

Bold/italic/code/link are *marks* attached to a run, not `**` characters
buried in text:

```json
{ "kind": "text", "text": "the spectacle is structural", "marks": ["strong"] }
{ "kind": "text", "text": "npm run dev", "marks": ["code"] }
{ "kind": "text", "text": "the official trailer", "marks": ["link"], "href": "https://…" }
```

The renderer turns marks into elements; nobody parses Markdown. (If shipping
marks in v1 adds too much prompt complexity, ship runs without marks and add
them in the next pass — the shape leaves room either way.)

### 4.5 The graph is untouched — that is the point

`nodes` and `relations` keep their exact current meaning. Graph, Table, and
Cells projections read **only** those two arrays and ignore `blocks`
completely. The reasoning engine does not learn that a heading exists.
Nothing about validation of tags/ids/relation endpoints changes; a new
section adds block checks on top.

### 4.6 How each projection now reads the one JSON

| projection | reads | ignores |
|------------|-------|---------|
| Document   | `blocks` (in order), resolving runs; node runs print `node.text` wrapped in `<span data-riemann-tag data-id>` | — |
| Graph      | `nodes`, `relations` | `blocks` |
| Table      | `nodes`, `relations` | `blocks` |
| Cells      | `nodes`, `relations` (editing a cell edits the node; block refs follow automatically because they point by id) | `blocks` |
| Structure  | the whole JSON, verbatim | — |

Document renders the blocks and nothing else. It still adds **no separators,
spaces, or line breaks of its own invention** between sentences in a
paragraph — paragraph breaks now come from the AI's block structure, which is
data, not a renderer habit.

## 5. The prompt shift

The contract prompt stops saying "You do not write prose." It cannot — prose
is now the product. It gains exactly one job: keep the two dimensions straight.

New rules in `contract/prompt.js` (replacing the plain-text-only rules):

1. Return one JSON object: `{ blocks, nodes, relations }`. Nothing else — no
   markdown fences, no commentary. (Unchanged in spirit.)
2. `blocks` are how the answer should READ: headings, paragraphs, lists,
   quotes. Write like an author.
3. `nodes` are the reasoning claims inside it: each `{ id, text, tag }`, tag
   only from the registered list. (Unchanged.)
4. A block never repeats a reasoning sentence: it references it with
   `{ "kind": "node", "ref": "<id>" }`. Blocks may add only small connective
   text that carries no claim of its own.
5. Every node must be referenced by at least one block. Every `ref` must
   match a real node id. Relations must join real node ids.
6. Style is expressed as blocks and marks, never as markdown characters
   inside text. `#`, `**`, `- ` in a text field is a contract violation.

The contract test grows: it must still name every registered tag, and now
also name every block type and run type, so prompt and schema drift is
impossible by construction (same trick as today).

## 6. The validation boundary grows, it does not soften

`validate.js` keeps Ajv-on-schema plus hand-written cross-checks. New
cross-checks, all failing visibly with specific errors:

- every `ref` in every block points at a node that exists;
- every node is referenced by at least one block;
- block `type` and run `kind` come from the closed lists;
- heading `level` is 1–6; `code` text is a string; etc. (schema-side).

The `VALIDATED` stamp and `Surface.open` behavior stay exactly as they are:
an AI reply that fails is shown in the chat and never becomes the Space. The
"never quietly repair" rule carries over untouched.

## 7. The edit path (patches) grows to stay honest

`patch.js` today can add/retag/remove nodes. With two dimensions, removing a
node that blocks still reference would leave dangling `ref`s the boundary
then rejects — so the edit ops must stay in step:

- `addNode` gains a required placement: which block/position the new sentence
  appears in (or a rule that the Cells view always appends a paragraph).
- `removeNode` must remove or clean the referencing runs in the same patch
  (one patch, one validation — never two half-editable lists).

This is the only place the two dimensions can fall out of sync through
human edits, so it is the place the boundary must be strictest.

## 9. Document projection: the React contract

`renderDocument` stops returning one flat string. It returns an ordered list
of described elements the UI mounts:

```text
[{ tag: "h1", runs: [...] },
 { tag: "p",  runs: [ { node: n1 }, { text: " In other words, …" } ] }, ...]
```

- node runs print exactly `node.text`, wrapped in
  `<span data-riemann-tag={tag} data-node-id={id}>` — tags are clickable
  metadata, never printed prefixes (existing rule, now with a home for it);
- the projection adds no whitespace of its own — every gap, break, and
  heading boundary comes from the AI's `blocks` (existing rule, honored by
  making structure the AI's job in data);
- marks render to `<strong>/<em>/<code>/<a>`.

## 10. Open questions (deliberately left open, answerable without rework)

1. **Marks in v1 or v1.1** — shipping `marks` on runs makes the prompt ask
   more of the model; the shape can land first and marks fill in later
   without breaking anything.
2. **Does a heading ever need to be a reasoning node?** Today: no (headings
   are pure presentation). If a title must later become citable/linked in
   the graph, the answer is a node referenced by a heading run — the shape
   already allows it.
3. **Multiple Space turns** — when the AI answers again, does the new JSON
   replace the Space or append to it? Out of scope here; the boundary
   behavior (adopt-or-reject) is the same either way.

## 11. Why this shape wins, in one paragraph

One AI reply, one pass, one stored object. The writer in the model gets to
write — as *structured data*, not as raw markdown to re-parse. The reasoner in
the model gets to reason — the graph keeps exactly the semantics it has
today, with no style pollution in it. The reader gets a modern document,
with every reasoning sentence still clickable, because tags ride *on* the
text as metadata instead of replacing the text. And every piece of the
original vision survives untouched: the JSON is still the model, projections
still only look at it, and the boundary still refuses — visibly — anything
that broke the contract.
