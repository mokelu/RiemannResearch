The short answer first: **you never comb through engines. You make each engine hand you a menu.** Then you only ever read the menu.

## The restaurant picture

```text
Symphony   = the customer, ordering by name
Menu       = the list of things that CAN be done
Waiter     = the dispatcher (LEDEN — it already routes everything)
Kitchen    = any engine
Adapter    = one small translator per kitchen
```

A customer doesn't walk into the kitchen to discover what the cook can make. They read a menu. The menu says three things: what the dish is, what you can choose about it, and how you'll know it arrived.

## A capability is just a card

```text
CARD: sort
  does:      puts a list in order
  needs:     the list            (a set from the DB)
             by                  (date / size / name)
  reports:   sorted              (an event)
```

That's the whole contract. What it does, what it needs, how you'll know it's done. The "needs" part is your params answer — the card is a little form.

## What happens with "Calendar, sort yourself"

```text
1. Compiler finds no built-in meaning for "sort yourself"
2. It asks the AI: "lower this — here is the menu"
3. AI reads the menu, finds "sort", fills the form:
      the list → Calendar's entries
      by       → date          (from context, or it asks)
4. Waiter delivers the filled card to Calendar's adapter
5. The adapter speaks Calendar's real language
   (a function call, a query, an HTTP request — the Symphony never knows)
6. Calendar does it, reports "sorted" to the stream
7. The test checks: unsorted before, ordered after → true → locked
```

If "sort" isn't on the menu, the AI lowers further: *read entries → order → write back.* Those are your DB primitives — the first cards on the menu. Lowering stops as soon as every piece is real.

One important rule: if a required field has no answer in the sentence or in the world, **the system asks**. That's not a failure. That's the form doing its job.

## "But all engines are different" — that's the adapter's problem

Inside the system, every command looks identical: a name plus a filled form. Outside, each adapter translates:

```text
"sort" card  →  a Python call      (one engine)
"sort" card  →  SQL ORDER BY       (another)
"sort" card  →  an HTTP request    (a third)
```

One wall socket, different plugs. Your Symphony never learns anyone's language. It only ever fills forms.

## "Do we comb through every engine?" No — cards arrive three ways

1. **The engine author ships one.** Like a new appliance coming with its plug.
2. **The AI drafts the adapter** from the engine's docs, you approve it, tests lock it. One-time work per engine — then it's on the menu forever.
3. **Generic adapters** for easy families — anything reachable by HTTP or command line can be carded semi-automatically.

So engine #50 costs you one adapter, not fifty rewrites. And the compiler never changes — it only knows the menu.

Bonus from your own architecture: since engines borrow state from the DB and own nothing, cards stay tiny. No state to describe, no secrets to expose. Params in, result out, everything through the DB.

## Where does the menu live?

**In your DB. It's just rows.** Capability knowledge is persistent data like everything else — consistent with "nothing owns state." Adding a card is an event. The AI's lowering step literally reads the menu table. And "what can you do?" becomes a free feature: list the cards.

I can't browse, so I'm not 100% sure which product you mean — I'll assume **trigger.dev** (if you meant Temporal, same answer; if it's something else, paste what it does and I'll map it). Here's what those do:

- You write a task — a function with a **declared list of inputs**
- The system **registers it by name**; anyone can trigger it by name + inputs
- The runtime handles delivery, retries, delays, durability
- Runs and results show up as **events you can build on**

That is exactly the menu pattern: capability = name + inputs + code, called by name, waiter handles delivery. Temporal does the same with "activities on workers." And the AI world standardized this as MCP: servers advertise tools as name + description + inputs, clients call blindly by card.

Three ecosystems, one idea. That's the best news in this whole reply: **the hard question — "how do engines expose capability?" — is already solved in the wild.** Your only new part is the front door: sentences fill the form instead of code.

## The symmetry this completes

```text
WATCH side:  raw events  →  composed UP into meanings      (pointer → hover → drag)
DO side:     sentences   →  lowered DOWN into primitives  (sort → read → order → write)

                    both meet at the primitives
```

One funnel up, one funnel down. A menu of happenings, a menu of doings.

And your reply side is free: "scan finished" and "engine failed" are just events on the stream — so "when the scan finishes, store the result" runs on the *same* CEP machinery as "when the button is pressed." A command is a watcher pointing the other way.

**One-liner: the Symphony never talks to engines — it talks to a menu. Every engine gets one adapter that makes it look like a menu item, and every filled order ends with a report back to the stream.**
